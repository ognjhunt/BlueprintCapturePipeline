# Native family execution

The beta path accepts pouring, wiping, insertion, stacking, button presses,
cloth folding and ordered combinations. A task family is not a robot capability
finding. Missing engine, asset, policy or authority evidence remains an explicit
preparation gap. Arm Decision Proof's frozen pair and claim rules are unchanged.

`family_native_prepared` completes only capture-backed CPU preparation. Its typed
result binds the task, native contract, runtime selection and scene revision,
and explicitly denies native application and policy execution. The website
forwards scientific contract digests; the Pipeline reopens the original sealed
contract and asset bytes instead of rewriting numbers across JavaScript.

The existing source scanner adopts the prepared family profile into beta
screening. Operator configuration supplies `native_runtime_source_receipt`,
byte-bound candidate execution specs and the private hosted-policy delivery
settings. `BLUEPRINT_TASK_FAMILY_RUNTIME_CATALOG_PATH` selects the protected
engine catalog. Captures can select a runtime ID and catalog digest, never a
factory import, executable or catalog path. Explicit policy selection pins its
candidate, configuration and catalog; otherwise compatible catalog candidates
can be compared under the existing site budget.

The engine catalog references an installed, qualified Gymnasium SDK registration
and a qualification receipt. Source and entrypoint bytes, qualification identity,
robot/controller/observation/action interfaces and staged assets are checked.
The SDK must implement `apply_native_task_contract`, `reset`, `native_state`,
`policy_observation`, `step_native_action` and `close`. Site qualification also
requires `set_robot_enabled`, `step_without_robot_action`,
`scripted_control_action` and `native_scene_readiness`. This release does not
install an unspecified simulator or manufacture its qualification.

Static readiness authorizes no physics claim. Within the existing canonical
allocation, every scenario first constructs fresh native robot-free,
zero-action and scripted-positive controls. Their native clocks, robot presence,
source assets, calibrated rendered cameras, reset invariants and independently
scored measurements must pass before loading or querying a candidate. Each
fresh candidate runtime rechecks its own native scene and cameras after reset.
Failures retain their receipts, media and cleanup evidence.

Family policies use the admitted native HTTPS observation/action interface.
Only the instruction, native RGB and proprioception enter inference. Model and
interface identity, action bounds, private credential origin, request counts and
worst-case hosted charges stay pinned. Runtime creation and queries remain
behind existing owner holds, consent, rights, cost, capacity, TTL, allocator and
provider-zero controls. No hold is released by preparation or deployment.

Initial comparisons use matched canonical reset seeds. They do not claim the
rigid lane's placement or lighting robustness. All cells retain native
measurements, action-delivery readback, lossless frames, review video, score and
runtime closure. Result admission replays the family scorer and site controls;
it does not invent `arm_moved` for another robot form. A delivered zero action
that fails the task is a scored policy failure, not a simulator void.

Only diagnostic counts, identities and closed-result digests are published to
the website's beta endpoint. The typed CPU preparation source must still match
the current capture and task. This does not grant a recommendation, promote a
scene, establish physical performance or replace a partner pilot.

`tests/test_task_family_production_path.py` exercises authenticated handoff,
source adoption, planning, the sealed bundle, the real worker entry, registered
SDK construction, controls, native action/state scoring, closeout and result
publication. Its installed SDK fixture and HTTPS transport are hermetic test
components; they are not live engine or GPU qualification evidence.
