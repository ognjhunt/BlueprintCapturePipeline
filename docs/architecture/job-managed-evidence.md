# Managed policy evidence for a commercial job

In the existing WebApp job workflow, a Blueprint operator can choose the job's
published fixed-arm setup and prepare a run without inviting a technology team
to operate it. Only an exact current permitted job/task scene is offered.
A draft may wait for footage, but assessment requires an actual retained video
receipt and current permission. Reusing evidence never substitutes for the
current source/task binding. Quick-10 is explicitly diagnostic; full matched
execution additionally requires its frozen matrix, exact per-cell construction
and controls, native runtime admission and existing bounded execution authority.
A job whose task has no supported scene or configuration keeps its video and
reports that capability gap.

The managed action reuses `configured-scene-offerings/:launchId/evaluation-setup`
and `evaluation-runs`, the published setup, preparation worker, and canonical
allocator. It preserves the frozen policy pair, independent scoring, policy-input
media, original resource authority, cancellation, expiry, and teardown. A failed
no-spend preparation delivery may be retried with the same immutable request;
this neither creates a new paid attempt nor renews its limits.

WebApp retains the immutable job/brief/task-context and capture/testbed source
fingerprint on the existing policy-run record. Source replacement or revocation
ends current applicability while preserving history; quote-only metadata does
not change scientific identity. Proposal creation, selection and agreement
revalidate references transactionally. Technology access, evaluation
participation and delivery interest are recorded separately. Accepted signed scientific publications retain their own
run, offering, configuration, plan, result and delivery digests. Owner job pages
project those results and limitations; proposals reference the exact accepted
result. A price change can stale a quote while leaving that evidence intact.
Earlier task results remain historical. Customer reports never enter this join.

Native v1–v3 scientific publications now include optional
`producer_canonical_json` bodies for each included plan, decision, delivery and
policy projection, excluding its own digest field. The receiver hashes the exact
producer bytes and checks semantic equality before accepting the existing
scientific digest. This preserves Python float serialization without rewriting
evidence identities. Legacy publications remain readable; canary v4 stays on its
existing RFC 8785 transport. The published legacy eight-family Quick protocol
retains its separately named object-cousin variation; it is not translated into
the exact-workcell primary matrix or the ADP 100-cell proof protocol.

The existing signed task-discovery publication and task-decision response also
carry original canonical bodies for discovery, individual candidates, decision,
and approved task. The website retains those bytes alongside the existing
artifacts through approval and compilation; candidate and approved-task IDs,
scientific digests, permissions, and approval truth remain unchanged.

Release the WebApp consumer and its `taskEvaluationPolicyRuns` job/time index
before the Pipeline producer. No deployment or provider execution is implied by
these source changes. Reproducible software-only transport fixtures live in
`tests/fixtures/managed_job_publication_v1/`; their generator runs local analytic
evidence and emits an incomplete-policy abstention, never a simulator or robot.

## Operator message drafts

These are unsent drafts for the existing workflow. Populate only from the
current job and permission scope; omit unknown commercial or scientific facts.
A draft, provider access or technical result never commits a delivery partner.

**Site — only material unknowns after video analysis**

“Your video is saved. Our reading is: [the analysis-derived summary]. Please
correct anything we misunderstood. To compare the available options, we still
need [the specific missing measurement or acceptance fact] because it changes
[the actual decision]. You do not need to write the job description again.”

**Delivery partner — comparable scope, availability and support**

“Blueprint is preparing options for [the confirmed job scope]. The proposed
acceptance terms are [the current measurable terms]. Technical evidence is
[the permitted evidence reference and its limitations]. Can you confirm whether
you can deliver and support this scope, where and when equipment is available,
and your installation, recurring operating/support costs, exclusions, required
site preparation and human assistance? Unknown items may remain unquoted while
we clarify them. Please separate assumptions and alternatives so the site can
compare proposals on the same scope. This request is not an award or a booking.”

**Technology provider — only when access or interface integration is missing**

“We need [the missing access, license term or interface] for [the bounded job
and robot/tool/sensor configuration]. Please confirm supported observations,
actions, version/deployment identity, access terms and availability. Assessment
permission does not include training, public reuse or unbounded footage sharing.
This access request does not assume that you install or support the deployment.”

No draft has been sent. Existing licensed interfaces require no repeated
per-job invitation. Real quotes, dates, availability and support commitments
must be recorded from actual partners before projection as their proposals.
## Capability routing

`src/blueprint_pipeline/job_capability_routing.py` routes a job's declared task
family against explicit task, embodiment and policy profiles built from the
existing registries. A supported profile returns complete configurations
(robot, tool, observation/action schema, controller, runtime, adapter and
pinned policy identity). Missing native coverage remains an explicit capability
limitation while the existing evidence router may still plan a bounded question
using an independently qualified analytical or other permitted method. Without
a qualified method, it plans abstention rather than inventing a result. This
does not admit native policy execution for that task; the job keeps its video
and brief. Unavailable robots (G1 pending a
verified episode and reviewed terms; Atlas, not accessible) and non-runnable
policies stay listed with their reasons. A new site on a supported profile
needs only data; a new task family or embodiment needs its adapter,
reset/scoring and evidence work plus one profile entry.
